## ADR-001: オンデマンドライフサイクルを備えた Daemon + CLI アーキテクチャ

### ステータス
承認済 (Accepted)

### 背景・コンテキスト
Headlessブラウザ（Chromiumなど）のプロセスは起動コストとメモリフットプリントが大きいです。従来のスクレイピングスクリプトのように、CLIコマンドやスクリプト実行ごとにブラウザをゼロから起動すると大きな遅延が発生し、ゾンビプロセスのリスクが生じるほか、連続するコマンド間で認証セッションやナビゲーション状態を維持できません。

一方で、ユーザーに手動でデーモンの常駐管理（`systemctl` や手動バックグラウンド起動など）を強制することは、手軽なCLIスクリプトやSDK統合における運用上の摩擦となります。

### 決定事項
**オンデマンド起動と自動クリーンアップを備えた「Daemon + CLI アーキテクチャ」** を採用します：
1. **オンデマンド自動起動:** `semcrawl open` などのコマンド実行時、デーモンが未起動であればCLIが透過的にバックグラウンドでデーモンプロセスを自動起動します。
2. **セッション分離:** デーモンは `session_id` ごとにブラウザコンテキスト、Cookie、タブを個別に管理・分離します。
3. **無操作による自動クリーンアップ:**
   - 設定された待機時間（デフォルト: 5〜10分）コマンドの受信がないセッションは自動破棄されます。
   - アクティブなセッションがゼロの状態で一定時間（例: 15分）経過した場合、デーモンプロセス自体が安全に自動終了します。
4. **明示的なデーモン制御:** デバッグや運用保守のために手動制御コマンド（`semcrawl daemon start`, `status`, `stop`）も提供します。

### 結果・影響
- **メリット:**
  - 2回目以降のCLI呼び出しにおいてブラウザ再起動のオーバーヘッドがなくなり、高い応答速度を実現できる。
  - アイドルタイムアウトにより、放置されたプロセスやメモリリークが発生しない。
  - バックグラウンドサービスの起動・停止を手動で意識する必要のないシームレスな操作性。
- **トレードオフ:**
  - プロセスの多重起動防止（ファイルロック）やセッション状態管理などの実装複雑性が増す。

## ADR-002: Unixドメインソケットによるプロセス間通信 (IPC)

### ステータス
承認済 (Accepted)

### 背景・コンテキスト
Semcrawl CLIとバックグラウンドのDaemonは同一ローカルマシン上で協調動作し、ナビゲーション、DOM探索、データ抽出を高速にやり取りするためのIPC（プロセス間通信）が必要です。

検討した選択肢：
- **ローカルTCP HTTP / gRPC:** 簡潔だが、TCPポート競合の発生、ファイアウォール警告、非ループバック露出時のセキュリティリスクがある。
- **標準入出力 (stdio):** 親子プロセス関係に密結合しやすく、複数CLI呼び出しや並行セッションからの共有が難しい。
- **Unixドメインソケット (UDS) / 名前付きパイプ:** ファイルシステムベースのIPCであり、ポート競合がなく、OSパーミッションによる安全で低遅延な通信が可能。

### 決定事項
**Unixドメインソケット（UDS）**（Windows環境では名前付きパイプ）上で、HTTP/RESTライクなJSONプロトコルを採用します：
1. デーモンは専用のソケットファイル（例: `$XDG_RUNTIME_DIR/semcrawl.sock` または `~/.semcrawl/semcrawl.sock`）を作成してリッスンします。
2. CLIはこのソケットファイルに対して直接接続します。
3. Goの標準ライブラリ（`net.Listen("unix", ...)` およびカスタム `DialContext` を設定した `http.Client`）を利用し、UDS経由でJSONベースの軽量HTTPリクエスト/レスポンスを行います。

### 結果・影響
- **メリット:**
  - ポート競合が発生せず、ファイルパーミッションによって保護された高速な通信。
  - デーモンのライフサイクルと個別のCLIコマンド呼び出しが疎結合に保たれる。
  - 標準的なJSONスキーマによりデバッグが容易で、将来のSDK実装も行いやすい。
- **トレードオフ:**
  - Windows環境に対応する際、名前付きパイプやローカルポートへのフォールバック処理が必要になる。

## ADR-003: `chromedp` の採用と Fetcher 抽象化レイヤーの設計

### ステータス
承認済 (Accepted)

### 背景・コンテキスト
現代のSPAや動的Webサイトをセマンティックにスクレイピングするためには、安定したブラウザ自動化ドライバが必要です。Goエコシステムにおける候補としては `chromedp`、`rod`、またはPlaywright/PuppeteerをNode.js経由で呼ぶアプローチが考えられます。

安定性、実績、外部ランタイム依存がないこと（Pure Go）、そして将来的な拡張（WebDriver BiDiや静的HTTPフェッチャー）を見据えた設計が求められます。

### 決定事項
1. **プライマリドライバとして `chromedp` を採用:**
   - Goエコシステムにおいて最も歴史と実績があり、Node.js等の外部ランタイムを必要とせずPure GoでChrome DevTools Protocol (CDP) を制御できるため採用します。
2. **疎結合な `Fetcher` インターフェースの導入:**
   - ページ遷移、要素評価、DOM抽出を抽象化した共通インターフェース `Fetcher` を定義します。
   - 初期実装: `ChromeDPFetcher`。
   - 将来実装: `BiDiFetcher`（Firefox等のクロスブラウザ対応用）、`HTTPFetcher`（ブラウザレンダリングを必要としない静的ページ向けの軽量HTTPクライアント）。

### 結果・影響
- **メリット:**
  - 最小限の依存関係で、実績のある安定したブラウザ制御が可能。
  - 将来ブラウザ以外のフェッチャーや他ブラウザ用バックエンドを追加する際にも、上位層のロジックを変更せず差し替え可能。
- **トレードオフ:**
  - 低レベルなCDP操作はコードが冗長になりやすく、適切なコンテキストやタイムアウトのハンドリングが必要。

## ADR-004: `TYPESAFE_API_KEY` を利用した自前 Jev 評価器と DOM プルーニング

### ステータス
承認済 (Accepted)

### 背景・コンテキスト
Semcrawlの最大の特長は、脆弱なCSS/XPathセレクタではなく、**Jev** 評価エンジンによるセマンティックなDOM要素特定です。評価器には以下が求められます：
- 階層的なセマンティッククエリ（例: `"検索結果 > 商品一覧 > 商品"`）の正確な解析。
- 外部のセマンティック評価API / LLM等との安定した連携。
- 巨大なDOMツリーのシリアライズや転送に伴うパフォーマンスオーバーヘッドとレイテンシの極小化。

### 決定事項
1. **Goによる自前実装 (In-House Implementation):**
   - Jevクエリパーサーおよび評価器をGoネイティブで実装し、メモリ使用の最適化、エラーハンドリングの統一、Semcrawl本体との密な連携を確保します。
2. **APIキー設定:**
   - 評価エンジンに必要なAPIキーは、環境変数 `TYPESAFE_API_KEY` から読み込みます。
3. **DOMプルーニング（枝刈り）戦略:**
   - 生のDOMスナップショット全体をそのまま評価エンジンに渡すことを防ぎます。
   - 非表示要素（`display: none`, `visibility: hidden`）、構造上のノイズ要素（`<script>`, `<style>`, `<iframe>`, コメント等）、冗長なラッパーコンテナを事前に除去した軽量DOMツリーを構築します。
   - クエリの階層セグメントごとに探索範囲を親から順に絞り込み（Top-down）、子孫ノード評価の計算量を削減します。

### 結果・影響
- **メリット:**
  - クエリ構文解析やキャッシュ、外部API呼び出しの挙動を自前で完全にコントロール可能。
  - プルーニングによりAPIに送信するトークン量・帯域・レイテンシを大幅に削減。
  - `TYPESAFE_API_KEY` による標準的かつ安全なキー管理。
- **トレードオフ:**
  - クエリ構文解析のAST管理やDOMプルーニングのヒューリスティクスを自前で保守する開発コストが発生する。
